# SecureWise runner security requirements

## Boundaries

- **Django control plane:** authenticates members, checks organization/project
  access and authorization, enqueues scans, and serves progress/findings.
- **Database:** shared source of queue/tenant state and result persistence;
  use TLS, least-privilege credentials and a private endpoint. Workers need
  only the database access required by the current Django application.
- **Worker host:** processes adversarial repository files and findings.
  Dedicated host, non-root service user, systemd hardening, bounded temporary
  storage, resource limits and redacted logs are required.
- **Scanner processes/containers:** untrusted inputs may exploit parsers or
  scanner bugs. Do not mount Docker socket, host home, secrets, or unrelated
  customer workspaces. The worker's Docker access is host authority.
- **GitHub credentials:** GitHub App credentials remain in control-plane/
  worker secret storage and are not copied into customer scanner processes.
- **Browser automation:** external browser navigation and unapproved origins
  must be blocked; synthetic test accounts only.
- **Artifacts/evidence:** tenant-scoped API access, bounded evidence and
  sanitized exports; no untrusted artifact path may escape its job workspace.

## Enforced/source-level controls

- Customer GitHub App scans are commit-pinned static archive scans and do not
  execute repository install/build scripts.
- Worker selection compares heartbeat, idle slot, scan-engine capabilities
  and architecture; a persistent active-job slot limits each worker identity
  to one job at a time. Unsupported or unknown architectures are not selected.
- Scan start and retry remain unqueued with HTTP 409 `status: blocked` when no
  fresh compatible worker can be selected.
- Scanner binary versions and architecture are dynamically recorded only when
  detected; Docker CLI availability is distinguished from daemon readiness.
- External URL requests require target ownership, separate active authorization,
  exact scope and per-request public DNS/pinned TLS/redirect validation.
  `SECUREWISE_URL_EGRESS_ENFORCED=true` is insufficient without a fresh
  root-owned proof file generated by the Linux nftables structural checker.
- Linux systemd example runs non-root with private temp/devices, read-only
  system paths, bounded CPU/memory/tasks and a private state directory.
- The opt-in `autopentest_api` profile is limited to one repository UUID and
  authorized authenticated-API sessions. It advertises the API capability only
  with a reachable rootless Docker daemon, the locally cached request-runner
  image, runtime builds enabled and an exact configured reviewed-content hash.
  Its Docker builds disable pulls and build-step networking and apply fixed
  memory/CPU caps; request containers are non-root and read-only.

## Unverified/required before customer beta

- A proof file is a root-controlled assertion plus structural nftables check;
  it is not cryptographic evidence or a substitute for independently testing
  actual firewall behavior and all routes/IPv4/IPv6/DNS/proxy paths.
- No Linux service deployment, host egress rules, rootless Docker, microVM,
  or cloud VM was exercised in this environment. `install.sh` intentionally
  does not install Docker or change firewall rules.
- The worker uses the shared production Django application/database identity
  and needs least-privilege/deployment hardening review; no per-tenant database
  credentials or cryptographic per-worker identities are issued to scans.
- Runtime builds stay disabled by default. The fixture-only profile and its
  offline/resource-limited build controls are source-tested but have not been
  deployed or exercised on Oracle. Reviewed content hashes and rootless Docker
  do not alone provide safe multi-tenant build isolation; use a dedicated
  disposable VM or microVM and independent host/network review before any
  customer builds.
- GitHub Actions ingestion, per-organization quotas, authenticated artifact
  storage, retention enforcement and signed downloads are not implemented.
- Scanner commercial license/rule-set obligations and update supply chain
  still require legal and operator review.

Never expose hostnames/worker IDs or infra secrets in customer API responses.
Never route to a weaker runner when an authorization, capability, architecture
or isolation requirement is missing.
